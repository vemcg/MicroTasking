# MicroTasking Defects

Field-testing defects found in shipped/branch builds. Feature-scope work lives in [PUNCH_LIST.md](PUNCH_LIST.md); this file is for "it's built but it misbehaves" bugs.

## 1. Manual Resume doesn't deliver a task promptly

**Symptom:** After manually restarting tasking (Pause → Resume / "Resume task queue"), nothing shows up for a while. It can be many minutes before the first task appears.

**Expected:** Manually resuming tasking should produce a task assignment (near-)immediately, subject to the normal queue-size and window rules. A manual Resume is an explicit "give me work now" gesture.

**Diagnosis (2026-09-07):**
- The Resume control (`onBackgroundPromptsChanged(true)` in `MainActivity.kt`) only flips the `background_prompts_enabled` pref. It doesn't trigger a delivery or a re-pace.
- While the app is foregrounded, delivery is driven by the pacing loop in the `LaunchedEffect` at `MainActivity.kt:338-373`. That loop sits in `delay(delayMs)` where `delayMs` came from `TaskDelivery.computeNextDelayMillis` — a semi-random paced interval derived from prompts-per-day and time remaining in the active window, routinely minutes long.
- The `LaunchedEffect` keys are `promptTasks, savedStartHour, savedEndHour, savedPromptsPerDay`. The Resume toggle is not a key, so toggling it neither restarts the loop nor recomputes the delay — the loop just keeps sleeping out the interval it already committed to.
- Background path has the same shape: the `AlarmManager` alarm was armed with the pre-Resume delay, so a Resume while closed also waits out the old interval.

**Possible fix (per Vern):** On Resume, run one delivery slot immediately (`TaskDelivery.deliverOrConsumeSlot`) and then recompute pacing — e.g. make `backgroundPromptsRunning` a `LaunchedEffect` key (or cancel/restart the loop), and re-arm the background alarm with a near-zero delay. Respect `maxQueueSize` and the active-window gating so Resume can't overfill the queue or force delivery where it shouldn't.

**Status:** Fixed on `tasking-revisited` (2026-09-10) as part of the dispatch-model rework. Pause/Resume now goes through `MainActivity.setBackgroundPrompts`, which persists the flag and then immediately runs `TaskDelivery.tick` — that re-paces and dispatches a task right away. The foreground loop also polls every second against a persisted `next_dispatch_epoch_ms` rather than sleeping out one long committed interval, and the on-screen countdown can be tapped to force a task immediately. Background alarm is re-armed from the same persisted epoch.

## 2. Countdown expiry never dispatches into a full queue, so tasks never auto-fail

**Symptom:** When the queue is full, the on-screen countdown runs down to zero and resets without anything being added to the queue. A task the user never acts on just sits there — it's never aged out / timed out. The only failure path left is a manual Abandon.

**Expected:** Every countdown expiry should dispatch a task. When the queue is already full, the new arrival pushes the oldest actionable task off the top, and that eviction counts as a timeout (a real automatic failure, breaking the streaks). This is the intended replacement for the old window-close abandon.

**Diagnosis (2026-09-10):** The `tasking-revisited` dispatch rework gated automatic dispatch on `underHalf` (`activeCount * 2 < maxQueueSize`) in `TaskDelivery.tick`. At or above half full — including completely full — the tick skipped, so the eviction/timeout branch (guarded by `activeCount >= maxQueueSize`) was unreachable except via a forced tap in rapid-testing mode.

**Status:** Fixed on `tasking-revisited` (2026-09-10). Automatic ticks now always dispatch; `underHalf` is gone. A full queue evicts-and-times-out the oldest actionable task on the regular cadence. A manual force-tap into a full queue in normal mode stays a no-op (only the automatic cadence times things out); in rapid-testing mode the tap still evicts. `RAPID_TESTING_THRESHOLD` also lowered 1000 → 500.

## 3. Duplicate task in the queue crashes the app on the task screen (crash-loop)

**Symptom:** "MicroTasking keeps closing" / "this app has a bug" the moment the task screen tries to render — repeatedly, so the app is unusable until its data is cleared. Seen on build 61 and much more frequently on build 63 (Galaxy S23, Android 16).

**Diagnosis (2026-09-10, from device logcat):**
```
FATAL EXCEPTION: main  (com.microtasking.app)
java.lang.IllegalArgumentException: Key "external-Decluttering-Empty one trash/recycling bin
that isn't empty yet." was already used. If you are using LazyColumn/Row please make sure you
provide a unique key for each item.
  at androidx.compose.foundation.lazy ... (task-queue LazyColumn, MainActivity.kt)
```
The persisted `task_queue` held two entries for the *same* task id. The task screen's `LazyColumn` keys items by `entry.task.id`, and Compose throws hard on a duplicate key — on every launch, before any pacing tick could repair the queue, so it crash-loops.

Root cause: `TaskDelivery.tick` picked the next task with `chooseWeightedTask(previousTaskId = <last actionable id>)`, which only avoids the single most-recent task, not everything already queued. With ≥2 tasks queued it could re-pick an earlier one and append it. Defect 2's "every tick dispatches" fix made this hit constantly (before, dispatch only happened at ≤1 actionable, where a collision was almost impossible). The user's leftmost category ("Decluttering", ~2× weight) collided first.

**Status:** Fixed on `tasking-revisited` (2026-09-10), three layers:
- `TaskDelivery.tick` now excludes every still-queued task id from the candidate pool before `chooseWeightedTask` (same guard `MainActivity`'s Substitute already used), and caps effective queue capacity at the eligible-pool size so a small pool can't force a repeat.
- `readTaskQueue` collapses duplicate task ids on load (`distinctBy { it.task.id }`, first wins) — repairs already-corrupt persisted state from older builds, which is what breaks the crash-loop for anyone already stuck.
- The task-queue `LazyColumn` key is now `"${id}#${index}"` so a duplicate can never crash the screen again.

Verified on-device (build `v0.1.7-64`, Galaxy S23 / Android 16): the previously crash-looping install — whose persisted `task_queue` held the duplicate — now cold-launches cleanly (0 crashes over repeated launches), and `tick` grew the queue to full with three distinct tasks.

## 4. Task dispatched before the active window opens; Pause doesn't stick; countdown ignores Pause

**Symptom (reported by Vern, 2026-09-11):** Active window 10:00 AM–6:00 PM. At 9:30 AM the task queue silently grew from 1 to 3. Pausing the task queue doesn't stay paused — something other than a manual Resume or the window opening keeps clearing it. Pausing also doesn't stop the on-screen "Next task in …" countdown; it kept counting down, and reaching zero appeared to be what un-paused things.

**Diagnosis (2026-09-11):** Two interacting root causes, both in `background_prompts_enabled` bookkeeping:
- `MainActivity.onCreate` unconditionally forced `background_prompts_enabled = true` on every cold launch ("pausing only lasts for the current running session" — a deliberate call made during the 2026-09-10 rework, now reversed at Vern's request). Android can and does kill the app between glances, so a relaunch silently undid a manual pause. Whichever moment the user next opened the app, `TaskDelivery.reconcile` ran *after* that forced write, and since reconcile only touches the flag at an actual window open/close transition, the forced `true` fell straight through untouched on any launch that didn't land exactly on a boundary — e.g. 9:30 AM, mid-way through the still-closed window.
- `TaskDelivery.tick`'s automatic dispatch path never checked the active window directly — only the `background_prompts_enabled` flag, which is supposed to track the window via edge-triggered transitions in `reconcileState`, but had no independent backstop. So the moment the flag above read `true` at 9:30 AM (pre-window), the very next tick dispatched immediately, and outside-window dispatch was generally only prevented as a side effect of the flag happening to be correct.
- `SettingsScreen`'s Save button had the same forced-`true` problem on every settings edit, not just first-time setup.
- Net effect on the countdown: a pause taken while outside the window was indistinguishable from the pre-existing "auto-paused because we're outside the window" state, so the countdown showed "Window opens in …" instead of "Paused," and the window-open transition (which is supposed to be one of only two legitimate un-pause triggers, the other being a manual Resume) fired regardless of whether the pause was automatic or an explicit user action — which is correct by Vern's stated rule ("only me or 10:00 AM should unpause it") for a pause taken *during* a still-open window, but wasn't reachable cleanly because of the two bugs above.

**Status:** Fixed on `tasking-revisited` (2026-09-11):
- Removed the forced `background_prompts_enabled = true` from `MainActivity.onCreate`; a relaunch now just runs `TaskDelivery.reconcile`, whose existing window-open/close transition logic is the sole automatic trigger.
- `TaskDelivery.tick` now hard-gates its non-forced dispatch path on `isWithinActiveWindow` directly, not just the flag — an automatic tick can never dispatch outside the window regardless of what set the flag. A forced/manual tap still bypasses this (existing "test outside the window" override).
- `SettingsScreen`'s Save no longer forces the flag on except for first-time setup completion.
- Added a **vacation mode** checkbox (Settings → Prompting Schedule): a separate `vacation_mode` flag, checked first in `TaskDelivery.tick` and `nextDispatchEpoch`, that blocks dispatch and alarm-arming unconditionally — including forced taps — until manually unchecked. Nothing else (not the window, not a relaunch) can clear it.
- Verified via `gradlew compileDebugKotlin` / `testDebugUnitTest` / `assembleDebug`. On-device verification still recommended for a first real-world pass, but this is no longer untestable in CI: added Robolectric (`app/build.gradle.kts`) so JVM unit tests can now exercise a real `Context`/`SharedPreferences`, and `TaskDeliveryTest.kt` covers this defect directly - regression tests for "no automatic dispatch before the window opens even if the enabled flag is wrongly true," "a manual pause clears the countdown and survives outside the window," "vacation mode blocks even a forced tap," and "reconcile never itself re-enables a manual pause." `TaskDelivery.tick`/`reconcile`/`nextDispatchEpoch` gained an optional `now: LocalDateTime` parameter (defaults to the real clock) to make this possible - no behavior change for real callers, all of which still call with the default.
  - **Gotcha for next time:** this dev machine's only installed JDK is 25 (see `gradle.properties`), and Robolectric 4.13's bundled ASM can't parse JDK 25's class file version ("Unsupported class file major version 69"). Bumped to Robolectric 4.17 (latest as of 2026-09-11), which resolved it, plus the `--add-opens` JVM flags Robolectric's docs require for JDK 17+ (`testOptions.unitTests.all` in `app/build.gradle.kts`). If Robolectric tests ever start failing with that same "Unsupported class file major version" error again after a JDK bump, check for a newer Robolectric release before assuming the app code broke.
  - **Follow-up hardening (2026-09-11, same day):** audited every place a "stupid" persisted setting (zero/negative/out-of-range window hours, queue size, or prompts-per-day) could reach live scheduling math. The Settings Save button already clamped these before persisting, but `TaskDelivery.loadSettings` - the one chokepoint every dispatch/pacing computation reads through - didn't re-clamp, so a value saved by an older build (before those Save-button clamps existed) or poked directly into SharedPreferences (e.g. over adb) could still reach `java.time.LocalTime.of()` (throws on a negative hour) or `List.take()` (throws on a negative count). Now clamped again at `loadSettings`: hours to `0..24`, prompts-per-day to `>= 0`, queue size to `>= 1`. Same fix applied to `MainActivity`'s own direct prefs reads that feed `makeTaskStack`/`isWithinActiveWindow`. Separately found and fixed a real (not just theoretical) crash: tapping **Substitute** on an already-queued task after the eligible task pool went empty (e.g. every category got unchecked while a task was still on-screen) called `chooseWeightedTask` on an empty list, which throws `NoSuchElementException` on `.last()` - now a no-op instead. Regression-covered in `TaskDeliveryTest.kt` (zero/negative queue size, negative prompts-per-day, out-of-range and blank window-hour strings - none of these should throw).

## 5. Tasks queued in close pairs - reopening the app (or Pause/Resume, or vacation mode) double-dispatches

**Symptom (reported by Vern, 2026-09-15, from `diagnostic.log`):** `QUEUED` entries showing up in tight pairs a few minutes apart (e.g. two around 4:30 PM, another pair a few minutes apart earlier the same day), rather than one per pacing interval.

**Diagnosis (2026-09-15):** `TaskDelivery.tick()` is the single place a task is ever appended to the queue, and by design (item 2 above) every non-blocked call to it dispatches - there's no "is a dispatch actually due" check inside `tick()` itself, only at whichever call site invokes it. Two call sites already gate on due time (the foreground 1s poll and the background alarm receiver, both checking `next_dispatch_epoch_ms` before calling `tick()`), but three others call `tick()` unconditionally with no such check: `MainActivity`'s "tick once on entry" (fires on every cold app open and every pacing-effect restart), Pause/Resume, and the vacation-mode toggle. Sequence that produces a pair: the background alarm fires, dispatches a task, and arms the next alarm hours out; the full-screen notification launches `MainActivity`; the entry-tick fires immediately with no check that a dispatch just happened seconds/minutes earlier, and queues a second task on top of the first. A bare Resume or vacation-mode toggle with no real interval elapsed does the same thing.

**Status:** Fixed on `tasking-revisited` (2026-09-15). `TaskDelivery.tick()` now gates the dispatch branch itself: a non-forced call arriving while the persisted `next_dispatch_epoch_ms` is still in the future just reconciles bookkeeping and returns without touching the queue or the schedule, leaving the already-armed dispatch alone. A forced tap (`force = true`), and any call that arrives once the epoch has actually elapsed (the 1s poll, the background alarm), are unaffected - so item 1's "Resume delivers promptly" still holds, because Pause/Resume and vacation-mode toggling both clear `next_dispatch_epoch_ms` before re-ticking, which reads as immediately due. Regression-covered in `TaskDeliveryTest.kt`: a second non-forced tick at the same instant no longer dispatches or touches the schedule, a forced tap still bypasses the gate, and a tick called once the armed epoch has elapsed dispatches normally.

## 6. "Window opens in N hours" is wrong after a forced tap outside the window

**Symptom (reported by Vern, 2026-09-25):** Active window 10:00 AM-6:00 PM. Woke up around 5-5:30 AM, and the countdown read "Window opens in 11 hours" - which would place the open time mid-afternoon, not 10:00 AM as configured. 10 AM is correctly ~5 hours from 5 AM, not 11.

**Diagnosis (2026-09-25):** Confirmed real by pulling `diagnostic.log` (`adb exec-out run-as com.microtasking.app cat files/diagnostic.log`) and matching it to the exact session: heavy activity between 04:58 and 05:12 that morning - repeated `QUEUED`/`STARTED`/`COMPLETED` entries, which can only happen outside the 10-18 window via a *forced* tick, since an automatic one is hard-gated to never dispatch outside the window (item 4). That activity is the "tap for one now" invitation in the countdown text itself being tapped repeatedly.

`next_dispatch_epoch_ms` serves two different purposes that got conflated: it's the background alarm's next-fire target (fine to compute via `fixedDispatchIntervalMillis` - "a plain fixed cadence, not a window gate," per its own doc comment - even outside the window), and, until this fix, it was also the literal source of the "Window opens in..." text. `TaskDelivery.tick(force = true)` bypasses the window gate, dispatches, and overwrites `next_dispatch_epoch_ms` with `now + fixedDispatchIntervalMillis(...)` - a pacing interval (here, `windowLength / (promptsPerDay - 1)` = 8h, or `24h / promptsPerDay` = 12h when the queue was already full - both derived from `prompts_per_day`, nothing to do with when the window opens). The very next render, still outside the window, displayed that pacing value labeled as "Window opens in X."

Two theories were tried and disproved by writing a test for each before landing on this one: (1) a settings change leaving a stale epoch behind - disproved because `tick()`'s outside-window branch recomputes unconditionally on every call, proven by `PacingSettingsChangeTest`, and disproved for this specific report because the log showed no window/prompts/queue-size change anywhere near that morning; (2) the displayed number being correct and Vern's own mental math being off - disproved once he confirmed the actual time (5-5:30 AM), which makes 11 hours impossible under correct math (max possible before a same-day 10 AM opening, from midnight, is 10 hours).

**Status:** Fixed on `bug-hunt` (2026-09-25). The "Window opens in..." text no longer reads `next_dispatch_epoch_ms` at all - `MainActivity` computes it live via `TaskScheduling.millisUntilWindowOpens(LocalDateTime.now(), startHour, endHour)` on every recomposition, exactly the same way `withinWindow` itself is already computed, so no forced tap (or anything else that legitimately repurposes the stored epoch) can throw it off. `next_dispatch_epoch_ms` and `fixedDispatchIntervalMillis` are otherwise untouched - the pacing/alarm-scheduling behavior they drive is correct on its own terms and wasn't the bug.

Two still-unresolved oddities turned up while reading the log, out of scope for this item: (1) two "Do Now" tasks (`65bc6fa8-…`, `bd158f21-…`) were `REFERRED` at 05:00:31/05:00:35 and then `QUEUED` again at 05:04:11/05:04:13 with no `completedForNow`/`fullyCompleted` event in between - worth its own investigation. (2) `queueSize=10` with `promptsPerDay=2` looks like a leftover test configuration, not a byproduct of this bug.

Regression-covered in `ForcedTapWindowCountdownTest.kt`: a forced tap outside the window writes a `next_dispatch_epoch_ms` that provably does **not** match `millisUntilWindowOpens` (the mechanism, reproduced directly); and `millisUntilWindowOpens` is unaffected no matter how many forced taps preceded it (the fix's guarantee). 129 tests total pass. Not yet verified on-device.

## 7. Countdown freezes solid when there's nothing eligible to dispatch; no message explains why

**Symptom (reported by Vern, 2026-09-25):** "If there are no cueable tasks available, the countdown timer stops. The window opens, and the time actually stops. Also, you don't get any message that says there's no cueable task."

**Diagnosis (2026-09-25):** `MainActivity`'s pacing `LaunchedEffect` (keyed on `promptTasks, savedStartHour, savedEndHour, savedPromptsPerDay, savedMaxQueueSize`) opened with `if (promptTasks.isEmpty()) { return@LaunchedEffect }`. That guard didn't just skip the tick call it was meant to protect - it also skipped the `while (true) { delay(1000); clockMillis = ... }` poll loop further down in the *same* effect, which is the only thing in the app that advances `clockMillis`. Every piece of UI that depends on `clockMillis` (the countdown text, the live "is the window open" check) is driven entirely by that loop, so once it never started, the display froze at whatever it last showed and stayed there - including reading "Window opens in ..." after the window had genuinely opened, since the live check that would have flipped it never ran either. Separately, nothing told the user *why*: an empty eligible pool (every category unchecked, or a fresh install with none selected yet) produced silence instead of an explanation.

The guard itself was never load-bearing for safety: `TaskDelivery.tick`'s `loadSettings()` already returns `null` - a harmless no-op, touching nothing, including `next_dispatch_epoch_ms` - the moment `eligiblePromptTasks(...)` is empty, before any dispatch/queue/scheduling logic runs. So removing the guard and always running the poll loop doesn't reopen the crash-on-empty-pool class of bug it might once have been defending against (see item 4's now-fixed `chooseWeightedTask`-on-empty-list crash, a related but distinct issue).

**Status:** Fixed on `bug-hunt` (2026-09-25). Removed the early return; the poll loop (and the "tick once on entry" call) now always run regardless of pool size. `TaskPromptScreen` gained a `hasEligibleTasks: Boolean` parameter (wired from `promptTasks.isNotEmpty()`), and `countdownText` gained a new leading case: `!hasEligibleTasks -> "No tasks available — check your enabled categories in Settings"`, shown instead of a stale or frozen countdown whenever the pool is empty. No coordination with ActiveTasks needed - this is Compose display logic local to MicroTasking, with no cross-app contract involved.

Regression-covered in `EmptyPoolCountdownTest.kt`: confirms `tick()` on an empty pool is a harmless no-op regardless of window or force, which is what makes always running the poll loop safe. A second test, `tick_currentlyDoesNotReconcileDayRolloverEitherOnAnEmptyPool_knownGapNotFixedHere`, documents (rather than fixes) a separate gap found while writing the first: `loadSettings()`'s `null` return happens *before* `reconcileState()` - the day/window rollover and streak bookkeeping - ever runs, so that bookkeeping also silently stops advancing while the pool is empty. Different symptom (stale streak/day state, not a frozen countdown) from what was reported here, so left unfixed and flagged for its own future item. 131 tests total pass. Not yet verified on-device.

## 8. A fully-completed (deleted) task briefly resurrects on the next Sheet sync

**Symptom (reported by Vern, 2026-09-25):** Using a test category with only two tasks. Occasionally, reopening MicroTasking briefly flashes a "ghost" - a task from that category that was fully completed (and so removed from the spreadsheet) a while ago - before it disappears again a moment later.

**Diagnosis (2026-09-25, jointly with ActiveTasks):** ActiveTasks investigated their own side first and confirmed it wasn't the cause: they send exactly one `fullyCompleted` broadcast per successful row deletion, with the correct category/description/taskId, and `TaskEventReceiver.onReceive` → `applyIncomingEvent` (`TaskEvents.kt:125`) removes the matching task from `managed_tasks` correctly and immediately the instant that arrives - confirmed by reading the code, not just asserted.

The actual gap is one step later, in the *next* Sheet sync. `mergeImportedManagedTasks` (`TaskPool.kt:219`) merges purely by id: `reconciled = imported.map { ... }` includes every row the CSV read just returned, full stop - there's no check for "this id was already removed locally, don't re-add it." Google's gviz/CSV export (the plain read path `MainActivity.kt` uses for tab enumeration and rows, as opposed to the Web App path used for Importance/Urgency) can lag behind a script-driven edit like ActiveTasks' row delete. If a sync lands in that lag window, `parseExternalTaskCsv` still sees the old, pre-deletion row, and `mergeImportedManagedTasks` treats it as legitimately still there - resurrecting it - until a later sync catches a fresher read and removes it again. That matches "occasionally" (the lag is Google-side and unpredictable) and "flashes then disappears" precisely.

This is the mirror image of a race ActiveTasks already solved on their own side (a stale/duplicate "referred" message racing their own completion) with a short-TTL `recentCompletions` map in their `TaskStore.kt` that a rebuild lays over the Sheet read - same shape of fix applies here in the opposite direction.

**Status:** Fixed on `bug-hunt` (2026-09-25). Added `RecentlyRemovedTasks.kt`: a SharedPreferences-backed, 10-minute-TTL set of task keys (taskId, or the legacy `category|description` key - the same identity rule referral matching already uses, `referralKeyOf`) that this device just removed via an incoming `fullyCompleted` event. `TaskEventReceiver` marks a key the moment `applyIncomingEvent` actually removes something for that event. `MainActivity`'s sync (`runSheetImport`) now filters every fresh CSV read (`filterResurrectedRows`) against the current marker set *before* `mergeImportedManagedTasks` ever sees it, so a stale cache read can't resurrect a row this device already knows is gone. The TTL comfortably covers gviz's typical cache lag with margin, self-prunes on every read/write, and isn't tied to any measured worst case - a real re-add of the same key more than 10 minutes after a genuine deletion isn't blocked. No change needed on ActiveTasks' side - confirmed by them: the broadcast and its payload are already correct and sent exactly once; this was entirely a MicroTasking-side gap in how the next sync treated a stale read.

Regression-covered: `RecentlyRemovedTasksTest.kt` covers the pure guard (`filterResurrectedRows`/`pruneExpiredRemovals`) in isolation - a row removed within the TTL is dropped, the same row is let through once the TTL genuinely expires, matching works via both the taskId and the legacy category+description key, unrelated rows are untouched, and the marker list round-trips through JSON. `TaskEventReceiverTest.kt` (new) covers the receiver wiring end-to-end via Robolectric: a `fullyCompleted` event that actually removes a task marks it removed; one that matches nothing (no-op) marks nothing; the legacy no-taskId path marks the right key; and `completedForNow` (task still exists, just un-referred) never marks anything removed. 136 tests total pass. Not yet verified on-device - this needs a real gviz lag window to trigger, which isn't reliably reproducible on demand.
